# タスクのプロジェクト間移動 設計メモ

タスクを別のプロジェクトへ移す。「起票したプロジェクトを間違えた」「担当チームが変わった」ときに、作り直さずにコメントやサブタスクごと移せるようにするのが目的。

ステータス: 実装済み（2026-09-26 時点）。#129（タスクを動かせるのをメンバーに限る）が前提。

## 方針の要約

- **1 件ずつ、ダイアログで移動先の設定を決めてから移す。** 一括移動は初期は対象外
- ステータスなどプロジェクトごとのマスタは、**同じ名前があれば自動で付け替え、無ければ利用者が選ぶ（ステータスは必須）**
- 担当者・依頼者・コメントの投稿者は、**移動先に同じユーザーのメンバーがいれば付け替え、いなければ外す**
- **移動は元に戻せない。** 失われるものをダイアログで具体的に並べ、確認のチェックを入れないと移動できない
- 移動の処理は 1 トランザクションで行い、途中で失敗したら何も変えない

## 権限

| 条件 | 理由 |
| --- | --- |
| **移動元と移動先の両方のメンバー**であること（テナント admin も同じ） | タスクまわりの作業はメンバーのみ（`docs/PROJECT.md` の「権限モデル」）。移動は両方のプロジェクトのタスクを変える |
| 移動先を閲覧できること | 見えないプロジェクトへは移せない |
| `readonly` ロールでないこと | 書き込みのため |
| 移動先がアーカイブされていないこと | アーカイブ済みのプロジェクトは新しいタスクを受け付けない |
| 移動先が移動元と別のプロジェクトであること | 同じなら移動ではない |

移動元の判定は既存の `ProjectAccessGuard`（ルートの `:projectId`）で行い、移動先は Service で `ProjectAccessService.assertAccess` / `assertEditor` を呼んで判定する。

## 付け替えのルール

| 項目 | 縛られ方 | 移動時の扱い |
| --- | --- | --- |
| ステータス | プロジェクトごとのマスタ | **必須で選ぶ。** 初期値は、移動元と同じ名前のステータス、無ければ移動先の初期ステータス（`is_initial`）。完了扱いのステータスを選んだら `completed_at` も付ける（通常の更新と同じ `resolveCompletedAt`） |
| ステータス更新日時 | ― | **移動した時刻にリセットする。** 移動先のステータスを設定し直す操作とみなす（新規作成時に作成時刻を入れるのと同じ考え方）。そのため、移動したタスクは移動直後は「動きなし」に出ない |
| 優先度 | プロジェクトごとのマスタ | 初期値は同じ名前の優先度。無ければ選ぶ（「なし」も可） |
| 担当者・依頼者 | ProjectMember | 初期値は、移動先で同じユーザーに紐づくメンバー。いなければ選ぶ（「なし」も可）。`user_id` の無い擬人化メンバーは同じ表示名で突き合わせる |
| タグ・フラグ | プロジェクトごとのマスタ | 同じ名前があれば付け替え。**無いものは外れる**（移動先にタグを自動で作らない。移動先のマスタを勝手に増やさないため） |
| 依頼部署 | テナント共通 | そのまま |
| 番号（`seq`） | プロジェクト内で一意 | **移動先で新しく振り直す**（例: #123 → #58） |
| 短縮コード（`short_code`） | 全体で一意 | **そのまま。** 共有リンク（`/:tenantKey/:shortCode`）は移動後も開ける |
| サブタスク | 親と同じプロジェクト | 一緒に移る（`project_id` を付け替え）。担当者・フラグは上と同じルール |
| コメント | 投稿者が ProjectMember | 一緒に移る（`project_id` を付け替え）。**投稿者は、移動先に同じユーザーのメンバーがいれば付け替え、いなければ空（NULL）にする。** 画面ではメンバーを削除したときと同じく「不明」と出る。「不明」になったコメントは、書いた本人も編集・削除できなくなる |
| 関連タスク | 両端が同じプロジェクトであること | **移動元のタスクとの関連は切る**（`task_relations` の行を削除） |
| 変更履歴 | タスクの ID で読み出す | **そのまま残る。**「◯◯から移動」を 1 件記録する（下記） |
| 通知 | プロジェクト＋番号でタスクへ飛ぶ | **`project_id` と `task_seq` を付け替える。** 付け替えないと、移動前の通知のリンクが壊れる（番号が振り直されるため） |
| 閲覧履歴（#126） | タスクの ID | そのまま |

「同じ名前」は、表示名（ステータス・優先度のラベル、タグ・フラグ・メンバーの名前）の**前後の空白を除いた完全一致**で判定する。

## 元に戻せないもの

移動先から元のプロジェクトへ移し直しても、次のものは戻らない。

- 移動元のタスクとの**関連**
- 移動先に無かった**タグ・フラグ**（サブタスクのフラグも含む）
- 移動先にいなかった**担当者・依頼者**（サブタスクの担当者も含む）
- 「不明」になった**コメントの投稿者**
- **番号**（元の #123 には戻らない）

ダイアログには、移動しようとしているタスクで実際に失われるものだけを、件数と名前で並べる。

```
⚠ 移動すると元に戻せません
  ・コメント 3 件の投稿者が「不明」になります（佐藤さん・鈴木さんが移動先のメンバーでないため）
  ・タグ「障害」は移動先に無いため外れます
  ・関連タスク 2 件との関連が切れます
  ・番号は移動先で振り直されます
□ 元に戻せないことを確認しました
```

## 画面の流れ

1. タスク詳細のスライドオーバーの見出しにある「別のプロジェクトへ移動」のアイコンを押す（移動元で編集できる人にだけ出す）
2. ダイアログで**移動先のプロジェクト**を選ぶ（自分がメンバーで、アーカイブされていないプロジェクトだけ出す）
3. サーバに**事前確認**を問い合わせ、付け替えの初期値と、失われるものを受け取る
4. ステータス（必須）・優先度・担当者・依頼者を確認・変更する
5. 失われるものを読み、確認のチェックを入れると「移動」が押せる
6. 移動したら、**移動先の一覧を開き、移動したタスクの詳細を開く**

## API

### `GET /projects/:projectId/tasks/:taskId/move-preview?to=:targetProjectId`

移動の事前確認。データは変えない。

- 返すもの: 付け替えの初期値（ステータス・優先度・担当者・依頼者）、付け替わるタグ・フラグと外れるタグ・フラグ、サブタスクで外れる担当者・フラグ、「不明」になるコメントの投稿者と件数、切れる関連の件数
- 権限は移動と同じ（プレビューで移動先の情報を漏らさないため）

### `POST /projects/:projectId/tasks/:taskId/move`

```json
{
  "targetProjectId": "…",
  "statusCode": "…",
  "priorityCode": "… | null",
  "assigneeMemberId": "… | null",
  "requesterMemberId": "… | null"
}
```

- ステータス・優先度・担当者・依頼者は、**移動先のもの**であることをサーバで検証する（画面の値をそのまま信じない）
- タグ・フラグ・サブタスク・コメントの付け替えは、上のルールでサーバが決める
- 1 トランザクションで行う。途中で失敗したら何も変えない
- 返すもの: 移動後のタスク（移動先の番号を含む）

## 変更履歴

`audit_logs` に **`action: 'update'`** で 1 件記録し、`changes` に「プロジェクト」（`field: 'project'`、移動元 → 移動先の名前）と「番号」（`field: 'seq'`、#123 → #58）を入れる。移動で変わったステータス・優先度・担当者・依頼者・タグ・フラグも、通常の変更と同じ形で入れる。担当者・依頼者は、同じユーザーのメンバーに付け替えただけなら記録しない（表示名が違っても同じ人のため）。

- `action` に `'move'` を足さないのは、`audit_logs.action` 列のコメント（許す値の一覧）とずれてマイグレーションまで要るため。画面の履歴は項目名の対応（`project` / `seq`）を足すだけで「プロジェクト: A → B」「番号: #123 → #58」と出せる

## 対象外（初期）

- 複数のタスクの一括移動
- Slack への通知（移動元・移動先とも送らない）
- 移動を担当者などへアプリ内通知すること
- 移動元の一覧に「移動しました」と残すこと（移動元からは消える）
- **公開 API（v1）での移動。** 元に戻せない操作を、失われるものの確認を挟まずに実行できてしまうため。具体的な使い道が出てから足す。事前確認と移動の処理はサービスに置き、画面用のコントローラは薄くしておくので、公開 API 用のコントローラを足すだけで済む。足すときは、失われるものを返すだけの `dryRun` を用意する（`POST /v1/projects/:key/tasks/:seq/move?dryRun=true`）
